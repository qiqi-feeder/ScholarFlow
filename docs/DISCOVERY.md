### 3.1 本轮建议的 Agent 设计重点

依据用户最新澄清，以下优先于旧页面划分和技术栈讨论，仍全部是助手建议，不是已批准的架构或实施顺序。

| 设计问题 | 推荐机制与具体行为 | 备选及代价 | 如何证明有用 |
| --- | --- | --- | --- |
| 同一句需求，在不同研究状态下应该做什么？ | 结合动作、对象、目标产物和已有材料选择下一步。例如“复现这个方法”：仅有论文先检查方法与代码来源；已有仓库先检查环境和数据；已有基线先核对复现条件 | 固定工作流更易检查，但中途接入僵硬；完全自由规划适应性强，但易漏必要条件。建议模型提出动作、程序检查可核验的前置条件 | 同意图/不同资产样例，检查缺失条件、误执行和必要澄清；不能只看意图分类准确率 |
| 如何把专业方法交给 Agent？ | 显式 Skill 优先，按任务加载选中正文、必要共享资源和条件参考；执行前检查缺失能力，记录方法与资源版本 | 全量加载简单但规则互扰；只给名字或摘要可能漏要求。按需加载也有路由与读取成本 | 同任务对比全量/按需加载的总成本、完成率和必要规则遗漏，未测前不声称节省比例 |
| 跨阶段如何保留必要信息？ | 项目材料保存事实和来源；任务历史保存探索过程；交接按下游目标选取约束、实验条件、结果引用、已确认结论与未决问题，必要时回查原文 | 整段历史容易噪声累积；纯摘要容易丢条件。建议结构化交接与可回查的版本材料结合 | 实验转写作时检查数据划分、数值、限制和来源；比较全历史/纯摘要/材料交接三种方式 |
| Agent 如何执行、发现错误并调整？ | 隔离环境内保留通用编程；实验提交、状态查询、结果比较和正式登记增加严格契约。网络问题可有限重试，代码错误可限次修复，结果未知先查询，条件不可比则补材料或停止比较 | 只有专用工具容易限制改模型；无边界重试会重复运行或耗尽预算。建议执行—观察—校验—修正有明确次数、成本和停止条件 | 注入超时、连接丢失、代码错误、不可比结果，检查重复提交、错误成功、恢复率与成本 |
| 如何防止阶段之间生成“看似连贯”的错误？ | 区分证据、假设、实测结果和推断；产物登记前校验，比较条件不满足时不能直接写优劣结论；依赖被替换/撤回时提示核对相关文字 | 仅靠末尾 Reviewer 可发现部分问题，但可能与生成者共享误解；确定性检查可查数值与引用，科学含义仍需模型/人工判断 | 设错引用、错数值、旧结果、混用数据划分的负例，观察发现率和误报，不能承诺自动判断全部科学正确性 |

将这些设计串成一个候选任务：“给定论文与基线代码，检查复现条件，完成一次受控修改和可比实验，再用真实结果生成实验分析与章节草稿”。保留效果未提升、实验失败和证据不足的合法结束路径，避免 Agent 为完成写作而编造正向结果。任务起点与范围仍等待用户选择。

多 Agent 是实现上述任务的一个选项：存在可独立核验的文献阅读或实验分支时再比较委派方案；连续调试或强依赖步骤不必硬拆角色。研究记录、校验和预算仍需统一。具体是否采用由任务对照决定。

### 3.2 建议收敛的三个核心机制

以下是 2026-10-20 接续讨论的建议，尚待用户确认；范围是产品机制，不是实现排期。

1. **面向研究状态的任务决策。** 路由到某个 Skill 只是入口，还要判断材料是否足够、下一步能否执行、何时需要补证据或回到前一步。建议允许 Agent 动态提出步骤，用可检查的领域条件约束动作；不要预设所有任务都经过同一条阶段链。对外展示任务依据、缺失材料和下一步动作即可，不要求用户理解内部 Profile/Session 概念。
2. **面向下游任务的上下文组织。** 文献到实验，传递方法细节、复现条件和仍不确定的实现点；实验到写作，传递可比条件、真实指标、失败/负结果和结论边界。交接材料应保留版本来源、缺失项与回查入口，不能把模型摘要当作已确认事实。Skill 加载和研究材料选择共同服务当前任务，分别记录各自成本与遗漏。
3. **有验证与停止条件的执行闭环。** Agent 可以编程、观察结果、限次修复和调整，但不能只以工具调用成功判断完成。对运行状态、产物结构、比较条件和结论依据分别检查；未知状态先查原任务，证据不足允许结束为待补材料，效果未提升允许形成负结果。领域检查与通用编程结合，比为每一步穷举工具更适合开放科研任务。

贯穿案例（候选）：用户要求“根据这些结果写实验章节”，系统发现两个结果使用了不同数据划分。应先解释不可直接比较的原因，保留已有结果；在授权和预算允许时建议补一组可比实验，否则写清限制或等待材料。补实验结束后重新比较，写作只引用通过核验的结果版本。用户若改变研究目标，应重新评估必要材料与既有授权，而不是继续原任务的剩余步骤。

该案例同时检验任务决策、专业方法加载、工具执行、失败处理和上下文交接。与只做路由分类相比，更能观察系统是否真的根据环境反馈改变行为。实验结果质量和事实正确性仍需独立检查，不能用 Agent 自评代替验证。

建议的取舍：三个机制都保留最小贯通行为，再选其中一到两个深入对照；多 Agent、自动探索树、长期记忆自演化等仅在已选任务出现明确需求时讨论。评测可以比较普通通用 Agent、加入科研 Skill、再加入材料/验证约束的行为差异；这些是候选对照，模型、工具权限、任务材料和总预算必须对齐，暂不规定数量和达标百分比。

### 3.3 论文复现的职责划分

状态：候选方案，尚未确认。用户询问复现应当做成 Skill 还是其他形态；以下职责划分仍是本轮建议，不代表已决定实现。初期任务范围已经在后续讨论中确认，以第 3.4 节和 C08–C10 为准。

建议以一个任务级复现 Skill（暂称 paper-reproduction）作为方法入口，由现有 Agent 执行，平台提供执行环境与可靠性约束。Skill 包装复现方法和资源，不单独承担进程调度或运行状态存储。暂不按论文建立一个 Skill，也不先拆出固定的读者/程序员/调试员团队。

| 职责 | 内容 | 承担者 |
| --- | --- | --- |
| 专业方法 | 怎样读出目标实验、查漏复现条件、处理官方代码/无代码情形、判断偏差及组织报告 | 复现 Skill：正文、按需参考、可选模板与校验脚本 |
| 动态决策 | 根据论文、代码、运行反馈和用户目标，决定补查、检查环境、修改、执行、继续诊断还是停止 | 执行该任务的 Agent；不要求另建固定角色 |
| 真实执行与约束 | 隔离文件/命令、资源预算、异步任务查询/取消、状态持久化、版本和产物登记 | 宿主工具与执行环境；Skill 文本不能代替这些保证 |

[Agent Skills 标准](https://agentskills.io/home)允许方法说明同时携带脚本、参考和模板，并按需加载。这里的职责划分是 ScholarFlow 候选设计，不是标准强制的架构。

入口先澄清“复现哪个结果”，例如某表格行、数据集、预测长度和指标；训练是否能跑只是其中一个检查，不能把“成功跑通”直接等同于复现成功。论文、附录、作者代码、配置和用户提供材料可互补，缺少论文某参数时应寻找来源或记录假设，不能悄悄补值。

| 模式 | 适用输入 | 应明确的来源与限制 |
| --- | --- | --- |
| 作者代码复现 | 有可用作者仓库/版本 | 检查配置、数据、预处理、依赖及论文描述是否一致；保留必要适配差异，不先改进模型 |
| 独立实现 | 无可用作者代码，或用户明确要求重实现；已确认不在初期范围 | 仅作为后续版本候选；未来若开展，需根据论文/附录实现并登记歧义和假设，不能称为官方实现 |

建议行为是条件驱动而非固定顺序：

1. 提取目标与复现条件，区分有来源事实、待核验配置、未知项和用户同意的假设。已有合格材料直接复用，不强制全文翻译。
2. 检查仓库/数据/环境/预算，必要时小规模验证数据与模型接口；小规模验证不能替代目标实验，也不能在跑不出时静默换更简单的数据。
3. 在授权范围内执行，记录代码、配置、数据划分、种子、环境和真实日志。先保留原基线，兼容修复单独记录；方法改动形成新的实验任务，不能混入忠实复现的结果。
4. 根据反馈做有限诊断：代码报错可修复，状态未知先查询，性能偏差先核对预处理/指标/训练配置，预算不足则停止或重新确认。不为了靠近论文数字反复利用测试集选配置。
5. 对齐比较条件，产出目标值/实测值/差异及解释依据。数值接近不保证实现忠实，数值不一致也不必然表示代码错；依训练随机性和约定评价，不预设通用容差。

最终可得到代码与适配差异、环境与配置、运行和指标、相对论文目标的对照、未解决问题/偏差说明及下一步建议。状态区分成功跑通、完成目标实验、在约定标准下复现达标、未达标、条件不足/中断；状态名称及落盘形式尚未定稿。

替代方案：一个巨大 Skill 包含全部学科细节，入口少但冗长且难维护；许多细粒度 Skill 可复用，但增加路由和交接负担。当前倾向一个复现入口配条件参考，只有发现独立任务有稳定输入/输出和复用需求时再拆分。领域相关预处理和评价必须适配，不承诺一个通用 Skill 忠实复现所有论文。

待确认：符合第 3.4 节准入范围的首条具体论文与目标实验、预算、容许的兼容适配和近似范围、复现报告的完成判定。独立实现已明确后置，不再作为初期二选一问题；尚未制定实施步骤。

### 3.4 初期复现范围与材料准入

状态：已确认需求（C08–C10，2026-10-20）；具体职责划分、工具和检查实现仍为候选，尚未进入实施。

用户确认两类输入均应支持：

| 入口 | 要完成的材料定位 |
| --- | --- |
| 论文 | 查找摘要或正文中的 GitHub 地址，并核对仓库与论文是否对应；用户无需另外抄出链接 |
| 模型名称 | 检索对应论文与 GitHub 仓库；若存在同名或近似名称，先核对目标，不能凭名称猜定仓库 |

初期把同时具备以下材料的论文纳入“可复现”范围：

| 编号 | 准入依据 | 需要保留的证据 |
| --- | --- | --- |
| R01 | 明确的 GitHub 仓库 | 仓库地址及其与论文/作者的对应依据 |
| R02 | 官方复现脚本与参数配置 | 对应目标实验的脚本、配置或明确参数说明；只有模型代码不能替代这些材料 |
| R03 | 多篇其他论文作为对比方法的复现依据 | 对应论文及其实验说明，能支持其他作者实际复现过；仅有引用或直接转载原论文数字不算 |

这是用户选定的初期任务准入标准，表示值得尝试执行，不保证当前机器、数据和依赖条件下必然成功。实际完成后仍须分别报告是否跑通、是否完成目标实验、是否达到约定复现标准。“多篇”的检索数量和证据检查细则尚未制定，不擅自设定阈值。

缺少明确 GitHub 仓库，或缺少官方实验脚本/目标实验参数配置时，初期标明“无法完整复现”（暂称），说明具体缺失项；不静默猜参数、拼凑实验流程或转为独立实现。此类任务留待后续版本考虑，不是判定论文永远无法复现。

进一步建议（尚未确认）：对尚未查明仓库、脚本或第三方复现证据的情况，保留“待核验”，说明查到什么、还缺什么；不能把“暂未找到”写成“确定不存在”。不满足 R03 时也不直接进入初期执行范围，具体展示名称待定。数据、依赖、硬件和预算在准入后仍需检查，其阻塞原因应与材料缺失分别说明。

本轮没有检索或认定某个具体模型已经符合标准，也没有确认独立实现、自动补全实验脚本或技术架构。

以下均为助手提出的候选设计和验证方向，尚未确认，更不是已实现能力或可直接声称的简历业绩：

后续用户明确要求先调研（C14）。本节候选暂不继续收敛为架构；先依据第 5.1 节的项目实现和效果证据重新审视，不能把本节建议当成调研前提或预定结论。

| 方面 | 科研任务中的问题 | 候选补充机制 | 如何验证自身贡献 |
| --- | --- | --- | --- |
| 工具与真实执行 | 训练超过单轮调用时长、连接断开后运行状态未知、重复提交浪费资源 | 在 Pi 工具扩展点上接独立实验执行器，保留隔离环境内通用编程；提交返回任务标识，支持查询/取消、提交去重、预算和产物检查。会话恢复与外部实验恢复分别处理 | 故障注入后统计重复执行、状态恢复正确性、取消行为和有效任务完成率；不能声称复用工具调用循环就是自研执行器 |
| 上下文 | 历史对话保留了探索过程，但跨任务容易遗漏实验条件，或继续使用被替换的结果 | 在已有会话/压缩机制上，按当前任务选择研究目标、已确认约束、材料版本、实验状态、关键结论及来源；原始材料可回查，正式事实不只存在于摘要 | 与相同 Pi 底座和领域 Skill 对照，检查长任务后的条件遗漏、旧结果误用、回查正确性，以及包含检索/摘要开销的总成本 |
| Skill | 已有按需加载不保证选对方法、环境可用或步骤完成 | 封装科研方法与资源；结合任务和材料选择 Skill，执行前检查依赖，记录版本，并以明确输入/产物及检查项验证。复现准入沿用第 3.4 节 | 检查方法误选/遗漏、依赖缺失处理和产物质量；区分采用现有加载机制与新增领域方法/检查，通用路由优化须单独对照 |
| MCP | 不同外部服务提供重复能力、输出不一致、失败语义不同 | 优先复用 Pi MCP 支持；围绕实际需求选择服务，补项目范围、权限策略和领域结果格式，按任务选用工具。工具隐藏或不提供给模型不等于已建立权限隔离 | 测试任务能否找到合适工具、越权调用能否被执行端拒绝、服务断开时能否保留正确状态；不把接入 MCP 或已有工具延迟加载当成协议创新 |
| 知识库与 RAG | 论文、代码、运行结果属于不同材料，检索到相关段落也不保证对应正确实验版本 | 先明确材料存储/版本与检索目的；论文按章节/页码组织候选检索，代码结合路径/符号/文本查找，实验指标按结构化条件查询；必要时再对论文做混合检索/重排，引用返回原始位置及版本 | 用有来源标注的问题检查证据命中、答案支持度、实验条件/版本匹配、跨项目混入与成本；不能用相似度代替事实正确性，也不预设必须引入向量数据库 |
| 完成验证与评估 | 工具正常返回、Agent 宣称完成，不保证结果符合科研任务要求 | 按任务检查文件、运行状态、指标条件和证据；保存成功、失败、材料不足及恢复案例，对自研机制逐项做对照 | 在相同模型、权限、材料和预算下比较基础 Pi、加入领域 Skill、再加入候选扩展的表现，必要时移除单项机制；暂不填完成率或节省比例 |

建议优先深入的三条技术主线是：面向科研任务的上下文组织、长实验的可靠执行、方法与结果的验证；MCP 和检索服务于这些问题。它们是待选择的投入重点，不是新增排期或固定架构。

简历与技术文档采用“问题 → 复用底座 → 自己新增的机制 → 可核验效果”组织。先区分未实现、已实现未验证、已验证三种状态；仅在实际完成后使用完成时态和真实指标。通过 SDK、扩展与宿主服务实现领域能力，不要求 fork 或修改 Pi 核心；是否需要核心修改必须由实际扩展点限制证明。

### 3.6 全流程工作台、协作与工作区组织

状态：候选产品组织，尚未确认；C03/C11 的全流程及真实可用工作台定位已确认，本节的编排、界面和边界是助手建议，不是实施授权。

建议围绕同一个研究项目贯通选题/文献、研究假设与方法、基线复现与方法开发、实验与分析、写作/引用/排版、投稿材料及审稿修改。用户可以从已有论文、代码、结果或稿件接入；写作发现缺证据、审稿要求补实验时返回相应任务，不强制按阶段一次通过。实际对外投稿操作仍需另定授权与集成方式，尚未确认自动提交。

| 概念 | 候选粒度与职责 | 用户体验 |
| --- | --- | --- |
| 项目工作区 | 一项持续研究；保存共同目标、来源材料、代码/数据引用、实验记录、结论与稿件 | 用户看到“研究项目”，能在不同任务之间继续工作，不为阅读/实验/写作重复建项目 |
| 任务会话 | 一次具体目标，如综述一个问题、完成基线实验、根据已核验结果写章节 | 同项目内可以分会话，避免一个无限增长的聊天；下游按需引用已确认材料和来源，不自动拼接全部历史 |
| 执行环境 | 按需要给代码分支、实验运行或子任务独立执行目录/沙箱 | 可隔离并行修改和运行；文件目录或项目名本身不构成操作系统隔离 |

候选 Agent 组织：用户对接一个主 Agent，主 Agent 根据研究目标与材料选择方法、调用工具和按需委派独立子任务。多篇文献的独立证据检查、互不修改同一成果的实验分支可比较并行委派；连续调试、相互依赖的修改和正式稿件整合由明确责任方协调。运行多份训练不等于必须启动多个推理 Agent；固定“研究员/实验员/写作者”团队不作为默认决定。若采用委派，任务目标、材料版本、预算、返回证据和修改范围必须明确，结果经核对后进入项目共同记录，不能让各 Agent 直接覆盖同一正式成果。

参考：查阅时 [DeerFlow Projects](https://github.com/bytedance/deer-flow/blob/059758f321d83dc7196e35fa99f5829333d97ec1/README.md#projects) 将相关会话、指令和文件架组织在项目中；其 Sub-Agents 说明主 Agent 可在有明确收益时委派，并隔离子任务上下文。[Anthropic Research](https://www.anthropic.com/engineering/multi-agent-research-system) 使用主控/工作者研究架构，同时讨论多 Agent 的成本和任务适配。这些是参考，不证明固定团队适合全部科研阶段，也不等同于本项目已实现编排。

候选界面：一个统一工作台入口，按研究项目组织；项目内可打开材料/阅读、代码/实验、结果/图表、稿件等工作面板，对话与当前任务关联。切换面板仍属于同一个研究项目，不为每个阶段建立独立系统；也不要求所有内容挤在同一个聊天流。默认展示材料、当前任务、需要用户决定的内容和产物，内部 Agent/Skill 技术细节可按需展开。具体布局、导航名称和 Web/桌面形态尚未定稿。

贯穿示例：围绕一个时间序列研究问题，先整理文献和研究缺口，再确定可检验的假设、选择并复现已有基线、实现修改并完成对照实验、分析真实结果、撰写与排版论文、准备投稿材料；收到审稿意见后在同一项目中补实验并修订文字。共享材料需要支持每次交接与回查，不能把复现报告作为整个产品的终点。

待讨论的是全流程各阶段的真实输入/产物与交接条件、用户在哪些研究决策上参与、什么任务值得委派，以及项目材料的共享/隔离粒度。保持能力模块化，用户围绕项目连续工作；不根据角色名称拆出互不相通的工作区。

| 单次阅读、写作、编程和工具调用 | Pi 与相应 Skill/工具已经能处理很多任务 | 沿用底座能力，在科研项目中提供连续交互，不声称这些基础能力是新增 |
| 多轮研究持续推进 | 用户可通过文件、Skill 和扩展组织材料与任务 | 开箱组织研究目标、材料版本、实验、结论和稿件，跨任务按需取用来源 |
| 长实验与恢复 | Pi 可调用运行工具，也可通过扩展接执行服务 | 提供实验记录、查询/取消、断连核对和预算约束，并明确区别会话与实验状态 |
| 从结果写论文 | Skill/工具或人工可进行核对，也可扩展程序检查 | 把运行、指标、条件和稿件引用连接起来，明确哪些可比较、哪些待核验；不保证自动判断全部科学正确性 |
| 全流程使用体验 | 用户可自行组合方法、执行、文件和展示方式 | 在统一研究项目下衔接调研、实验、分析、稿件、投稿材料和审稿修改 |

差异是候选产品交付和领域机制，不是 Pi 的理论能力上限。若给 Pi 配置相同扩展与服务，也可能实现接近的行为；需要诚实说明复用和新增部分。若只完成外观和预装 Skill，主要价值是交互与配置便利，不能据此声称已提升科研可靠性。可验证的后续目标是减少跨阶段材料丢失、重复实验和错误比较等实际问题；目前尚未测得这些改进。

默认技术建议：本地浏览器界面＋TypeScript 服务＋Pi SDK，SQLite 存项目元数据，文件保存产物；Agent 大语言模型按 C16 使用 API。本地运行不自动等于模型离线，也不自动承诺论文内容不经过模型服务。实验按 C15 采用 Windows＋Conda，Git Bash 可作为命令入口；显式记录环境路径、工作目录和进程，支持日志/退出码、超时/取消及恢复核对。只有目录/Conda 不构成操作系统隔离。核心研究问题/实验方案及运行预算由用户确定，授权范围内自动处理工作版本，正式定稿明确保存版本。

术语澄清：**Agent 大语言模型（LLM）**指驱动 Pi 理解需求、规划、选择 Skill、调用工具、分析和写作的推理服务；**科研实验模型**指被训练/评估的 STGCN 等方法；**Conda 环境**如用户提到的 stgcn2 是依赖/解释器环境，不能仅凭环境名称推断其中项目、PyTorch/CUDA 或复现条件已经满足。Agent LLM 已确定走 API，科研实验仍在 Windows 本地执行，两者独立配置。

API 接入参考与候选范围：固定版本 Pi 文档已列出 DeepSeek 等内置提供方；优先复用底座接入，自定义兼容端点使用模型配置，特殊协议或鉴权再评估提供方扩展。建议首批以 DeepSeek 为必选，另评估通义千问和智谱；后二者具体套餐、区域及端点必须分别核对，不能把 Pi 的 Qwen Token Plan / ZAI Coding Plan 支持扩大为所有对应厂商 API 均可直接使用。这是接入建议，尚未实现或通过真实 API 验证。[Pi 提供方文档](https://github.com/earendil-works/pi/blob/a731ba8b80ac56662b4ca7f09102f94447862d8c/packages/coding-agent/docs/providers.md)、[Pi 模型配置](https://github.com/earendil-works/pi/blob/a731ba8b80ac56662b4ca7f09102f94447862d8c/packages/coding-agent/docs/models.md)

执行参考：Conda 官方提供 `conda run` 指定名称或环境路径运行命令，并可配置工作目录和实时输出；具体优先采用明确路径的 Conda 调用，避免依赖每次交互式激活。Git Bash 路径/参数转换、Windows 子进程树取消和编码须在真实环境验证。[Conda run 文档](https://docs.conda.io/projects/conda/en/stable/commands/run.html) 当前仅检查 Git Bash 可启动；未定位 Conda 后，用户已确认当前环境没有，要求暂缓处理。不再继续查找或安装，不作为当前讨论/写计划的阻塞；真实实验验收前仍需准备并验证环境，尚未运行训练或改动环境。

## 4. 已发现的设计问题

1. **旧主线可能偏离目标。** 旧路线把完整双语阅读、写作、实验串成 M5 → M6 → M7；这是一种交付顺序，不是天然科研依赖。已有代码/结果的用户不应必须先全文翻译才能分析或写作。建议按任务前置材料讨论闭环，尚未确定替代顺序。
2. **工具限制存在冲突。** 旧方案关闭内置通用工具，仅列专用接口；S2 则强调隔离环境内改代码、数据处理与画图。需要区分“禁止宿主任意执行”与“保留沙箱内通用编程”，不能混为一谈。
3. **文件版本不等于结论有效。** 已有 Artifact/Run/hash 设计有价值，但文件可追溯仍不能证明比较公平或文字成立。建议登记图表/结论的明确依赖，变化后标记待核对；不得承诺识别所有自然语言隐含依赖。
4. **依赖变化也不等于结论已错误。** 新增一个实验不一定替换旧结果；旧稿仍可正确引用旧版本。需区别追加、替换、撤回、数据失效，显示核对原因，不能自动重写用户确认的结论。
5. **“运行成功”与“科研有效”需分开。** 退出码正常、生成 CSV 或写出 PDF，都不足以证明结果可比。应检验数据划分、预处理、指标口径、资源与种子；不能用测试集反复调参后宣称泛化提升。具体校验深度待定。
6. **审批粒度决定是否好用。** 所有编辑都审批会打断迭代，完全自动又容易覆盖既有成果。可讨论在授权预算内修改实验草稿，涉及正式稿件、扩大资源或外部提交时确认；这仍是建议。
7. **概念数量过多。** Profile、Workspace、Skill、Session、Run 同时暴露会提高用户负担。它们可用于内部分析，但界面是否需要用户逐一选择须由真实任务证明。
8. **既有测试锁定了旧方案。** 架构测试强制 M1–M8 链式依赖、产品测试检查固定关键词；只能证明文档自洽，不能证明需求正确或真实功能可用。未来若调整范围应同步调整测试，不让测试反过来决定产品。
9. **还缺资源边界。** 时间、模型费用、运行设备、数据与目标任务未明确，现在冻结架构会把未经验证的假设固化。
