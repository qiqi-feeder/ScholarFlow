## 1. 决定来源

- S1：用户指出切换页面后无法对话，要求先讨论、不编码。
- S2：用户确认“会话始终右侧”，继续讨论其余工作区如何分配。
- S3：用户认可围绕具体任务组织内容、保护工作现场和后台反馈的方向，并明确要求对话框支持模型切换。
- S5：用户放弃最后一轮 Stitch 改稿，要求按原稿和问题清单准备实现；精确资源及排除列表见 PLAN 第 8.7 节。
- S6：用户确认本次文献获取、全工作区反馈、单主 Agent 动态装配的讨论作为大框架；各工作区的工具细节后续逐项讨论。
- S7：用户在讨论自我进化、跨任务记忆与冲突后要求进入实现阶段，先同步文档；含金量排序不作为实施顺序。

## 4. Agent 与文献能力的大框架

按 S6 确定：每个任务保留一个主 Agent 会话；开始只提供少量基础工具和简短能力目录，需要时由主 Agent 请求加载能力，由宿主校验并启用对应工具、读取相关 Skill。无需每轮额外调用模型做意图分类，也不按页面强制限制能力。不建立固定多 Agent 团队；独立执行上下文暂为后续评估项，下载/训练/编译 worker 不算 Agent。

Skill 提供方法，Tool 执行有明确输入输出的动作，MCP 是可选外部连接方式，知识库保存可回查的资料与证据。当前 `load_skill` 仅读取说明，不会自动启用工具；动态装配是后续改动，不能记成现有能力。

文献既支持找指定论文，也支持按主题、时间范围收集和整理研究方向。优先建设稳定的“身份确认 → 公开全文解析 → 下载及校验 → 保存全文/来源 → 自动入库”路径。Crossref 元数据不等于全文；无公开副本、网络不可达、需授权、解析失败分别反馈，支持用户导入已有文件。全文/页码证据与简短笔记分开保存；不承诺无代理能访问所有来源，也不把未读全文说成已读。

所有工作区遵循“工具执行 → 后台保存真实记录/文件 → 事件通知 → 工作区更新”：论文下载后进入列表，实验产物进入运行与结果视图，稿件保存后编译并显示对应版本的 PDF。状态、断线恢复、旧版本和失败原因都必须可回查，不能仅靠聊天宣布完成。工具名称、参数、供应商、Skill 拆分及各工作区细节后续讨论，详见架构文档。

按 S7 纳入持久记忆及冲突规则、经验提炼和受控 Skill 进化。先做能力/有界上下文和记忆基础，再做独立评测及发布；来源、范围、版本、争议与确认可查。参考 Harness²、mem0、Graphiti 机制，DREAM-RSI 探索树回放本期不接入；细节见实施规格。
